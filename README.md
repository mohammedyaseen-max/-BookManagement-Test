# Book-Crossing Big Data Analytics

An end-to-end Big Data Analytics project built on the Book-Crossing dataset. Apache Spark 3.5.6 / PySpark provides distributed-style data engineering, Spark SQL analysis and MLlib modelling. Parquet stores analytical datasets, while MongoDB is an optional serving layer for recommendation outputs.

## Project objectives

- Assess the quality of the Books, Users and Ratings source tables.
- Clean, integrate and transform the data with PySpark.
- Explore rating behaviour, book popularity, user activity and publication-year patterns.
- Compare Spark MLlib ALS and Random Forest against a global-mean baseline.
- Measure runtime behaviour at 25%, 50% and 100% data-volume levels with repeated runs.
- Export a compact ALS top-10 recommendation result to MongoDB when the service is available.

## Technology stack

- Apache Spark 3.5.6, PySpark, Spark SQL and Spark MLlib
- Apache Parquet for columnar analytical storage
- MongoDB 7.0 with PyMongo for optional recommendation serving
- Python 3.11
- Java 17 (OpenJDK / Temurin)
- Matplotlib for generated figures
- Docker Compose for reproducible local services

## Dataset

The project uses the Book-Crossing dataset:

- `Books.csv`: book metadata.
- `Users.csv`: user attributes.
- `Ratings.csv`: user–book rating interactions.

Place the original files under `data/raw/` using their original filenames. The processed Parquet datasets are generated by the preprocessing pipeline and are not committed to Git.

## Run with Docker Compose (recommended)

The Spark and MongoDB services are defined together in `docker-compose.spark.yml`. Compose places both services on the same default network; Spark reaches MongoDB using the service hostname `mongodb`. MongoDB data is persisted in the named volume `mongodb_data`.

Build and start both services from the repository root:

```powershell
docker compose -f docker-compose.spark.yml up -d --build
docker compose -f docker-compose.spark.yml ps
```

Run the preprocessing pipeline inside Spark:

```powershell
docker compose -f docker-compose.spark.yml exec spark python analysis/inspect_dataset.py
docker compose -f docker-compose.spark.yml exec spark python analysis/clean_with_spark.py
```

Run quality checks, EDA and models after preprocessing has completed:

```powershell
docker compose -f docker-compose.spark.yml exec spark python models/data_quality_audit.py
docker compose -f docker-compose.spark.yml exec spark python analysis/quality_checks.py
docker compose -f docker-compose.spark.yml exec spark python analysis/relationship_checks.py
docker compose -f docker-compose.spark.yml exec spark python analysis/eda_with_spark.py
docker compose -f docker-compose.spark.yml exec spark python analysis/extended_eda.py
docker compose -f docker-compose.spark.yml exec spark python models/als_recommender.py
docker compose -f docker-compose.spark.yml exec spark python models/random_forest_rating.py
docker compose -f docker-compose.spark.yml exec spark python models/fair_model_comparison.py
docker compose -f docker-compose.spark.yml exec spark python models/als_tuning.py
docker compose -f docker-compose.spark.yml exec spark python models/scalability_experiment_repeated.py
docker compose -f docker-compose.spark.yml exec spark python analysis/create_visualizations.py
```

The ALS script always writes its CSV recommendation output locally. It then attempts to write the same top-10 recommendations to MongoDB collection `book_analytics.als_top_recommendations`. MongoDB export is deliberately best-effort: if MongoDB is unavailable, the script prints a warning and completes without discarding the Spark outputs.

For local execution outside Docker, the script defaults to `mongodb://localhost:27017/`. Override the connection string with `MONGO_URI` when needed. In Docker Compose, `MONGO_URI` defaults to `mongodb://mongodb:27017/`.

Stop services without deleting persisted MongoDB data:

```powershell
docker compose -f docker-compose.spark.yml down
```

To remove the MongoDB volume as well (this permanently deletes stored recommendation documents):

```powershell
docker compose -f docker-compose.spark.yml down -v
```

## Complementary Technology & Architecture Justification

### Apache Spark: analytical processing

Apache Spark 3.5.6 is the computation engine for ingestion, cleaning, joins, aggregations, feature preparation and MLlib model training. Keeping transformation and model workloads in Spark allows the project to use a consistent distributed-processing API and scale those workloads beyond a single machine when deployed on a cluster.

### Apache Parquet: columnar analytical storage

Parquet is the storage format for cleaned datasets such as `books`, `users`, `ratings` and `ratings_enriched`. Its columnar layout is well suited to Spark SQL and MLlib workflows that repeatedly read selected columns, filter records and aggregate large tables. It also separates expensive raw CSV parsing from downstream analytical jobs. Parquet is a file format, not a database or a replacement for Spark.

### MongoDB: NoSQL recommendation-serving layer

MongoDB 7.0 is integrated as a complementary document store for the compact top-10 recommendations produced by ALS. PyMongo writes documents to `book_analytics.als_top_recommendations`, including the user ID, ISBN, predicted rating, rank and generation timestamp. A document database provides a convenient serving-oriented representation for application/API retrieval without requiring downstream consumers to scan analytical Parquet datasets.

This separation reflects two distinct workloads:

- **Analytical workload:** Spark processes large source and feature datasets, with Parquet as its columnar storage layer.
- **Serving workload:** MongoDB stores a small, queryable recommendation result that can be retrieved by user ID by a future application or API.

MongoDB is an optional output sink, not a dependency for Spark preprocessing or model evaluation. The ALS script uses a short connection timeout and catches MongoDB errors so analytical results remain available even when the database is offline. The local Compose setup is a single-host demonstration; it does not claim to be a production distributed MongoDB cluster.

## Execution order

Run commands from the repository root so paths resolve consistently:

1. Inspect the raw dataset: `python analysis/inspect_dataset.py`
2. Create processed Parquet datasets: `python analysis/clean_with_spark.py`
3. Run data-quality checks and EDA.
4. Train and evaluate ALS, Random Forest and the fair comparison.
5. Run the repeated scalability experiment.
6. Generate figures from saved outputs.

Run each stage only after its input stage has completed successfully.

## Evaluation approach

The project reports RMSE and MAE (lower is better), alongside evaluated-row counts and ALS prediction coverage. ALS may omit predictions for unseen users or items when cold-start handling is enabled. The scalability experiment uses fixed sample fractions of 25%, 50% and 100%, with repeated runs to report mean runtime and standard deviation. Runtime is environment-dependent and should be regenerated on the machine used for the final report.

## Results

Generated metrics, CSV outputs and figures are stored under `analysis/results/`. These historical outputs are not a substitute for rerunning the scripts after changing code, data, Spark settings or model parameters.
